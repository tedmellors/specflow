#+TITLE: SpecFlow – System Overview
#+STARTUP: overview

* Purpose

SpecFlow is an Org-native workflow and set of Emacs tools for *spec-driven,
phase-gated, AI-assisted software development*.

The SpecFlow methodology can be used without tooling (via conventions and
=CLAUDE.md= rules). This package provides Emacs commands, templates, and
shortcuts that automate common SpecFlow operations.

Its primary goal is to help developers use AI assistants (e.g. Claude, GPT)
*without losing control* over:
- requirements
- scope
- architectural intent
- project state
- review boundaries

SpecFlow is designed for real software projects, not demos or throwaway prototypes.

* Problem Statement

AI assistants fail in predictable ways during software development:
- jumping from vague intent directly to implementation
- inferring requirements that were never stated
- drifting scope across modules
- rewriting large areas of code or docs “for clarity”
- losing track of what phase the project is actually in

These failures are not model bugs — they are workflow failures.

SpecFlow addresses this by making project state, intent, and constraints
*explicit, structured, and enforceable* using Org-mode as the source of truth.

* Key Concepts

*Unit*: A bounded scope of work (module, component, or service) with its own
specification, TODOs, constraints, and lifecycle phase. Units are treated as
independent execution targets within the project.

*Control Plane*: An Org file (e.g. =docs/specflow.org=) that stores the
authoritative project state: current phase, active unit, and unit registry.
Used by SpecFlow tooling and AI workflows to determine what work is allowed.

*Phase Transition*: A phase ends when its required artifact is produced and
explicitly approved by the human. The control plane is then manually updated
to the next phase. AI assistants do not advance phases autonomously.

* Core Principles

*1. Explicit State*
The current phase, active unit, and canonical artifacts are stored in a control plane
Org file, not inferred from chat history.

*2. Phase-Gated Work*
Work proceeds strictly through phases:
Plan → Specify → Scaffold → Implement → Validate → Document

Each phase allows only certain actions and artifacts.

*3. Specs Before Code*
Specifications are short, explicit, and authoritative.
Code must conform to specs; specs do not emerge from code.

*4. Outcome-Based Tasks*
TODOs describe outcomes and behaviors, not vague actions.

*5. Human-in-the-Loop Authority*
The human explicitly approves phase transitions and scope changes.
AI assistants propose; they do not decide.

*6. Minimal Diffs*
Generated or updated artifacts should change only what is necessary.
Unrelated formatting or restructuring is avoided.

* What SpecFlow Is

- A lightweight development discipline
- A set of Org conventions
- An Emacs-centric toolchain
- A guardrail system for AI-assisted work

* What SpecFlow Is Not

- A project management SaaS
- A replacement for Git, CI, or testing frameworks
- An autonomous coding agent
- A prescriptive repo layout (beyond control-plane + unit pointers)

* Target Users

- Emacs users who already rely on Org for planning and design
- Solo developers and small teams
- Developers who want to use AI assistance safely and deliberately
- Projects where correctness, auditability, or reasoning quality matters

* Production-Ready (Definition)

For SpecFlow itself:
- deterministic behavior
- predictable file modifications
- reliable parsing and writing of Org structures
- tests for core logic

For projects using SpecFlow:
- reliable within declared scope
- testable and reviewable
- auditable where reasoning or decisions occur
- not necessarily infrastructure-final or feature-complete

* Success Criteria

SpecFlow is successful when:

- A developer can open a repo and immediately see:
  - current phase
  - active unit
  - what "NEXT" means
  - where specs and TODOs live

- AI-assisted work becomes:
  - more deliberate
  - easier to review
  - less error-prone

- The tooling reduces cognitive overhead rather than adding process burden.

*Measurable criteria:*

- Time-to-orient: A contributor can identify active phase, active unit, and
  NEXT task in under 30 seconds.
- Guardrail effectiveness: Phase-incompatible SpecFlow commands refuse to run
  (or warn) before file modifications occur.
- Bundle completeness: The context bundle command includes control plane,
  NEXT task, unit spec/todo/rules, and parent chain within one invocation.
- Determinism: Running context bundling twice without repo changes produces
  identical output.

* Open Questions

- How much enforcement should be "hard" vs advisory?
- What UI surfaces are most effective in Emacs (mode-line, buffer, transient)?
- How should SpecFlow scale to multi-repo or monorepo setups?
- Should phase transitions be recorded as git commits (or included in the same
  commit as the phase's artifact), or can they be lightweight edits to the
  control plane?
