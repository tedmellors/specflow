#+TITLE: specflow-hydrate – Specification
#+STARTUP: overview

* Purpose

=specflow-hydrate= provides *framing*, not a workspace.

It helps the user start and maintain a *SpecFlow-correct* AI conversation by:
- reading the control plane state (via org-store)
- extracting the canonical NEXT task (from root =todo.org=)
- generating a phase-correct "conversation header" + prompt scaffold
- optionally warning when AI output appears to violate the current phase

It does *not* replace Claude Code IDE, window layouts, or buffer workflows.
It is designed to work with any AI chat surface (Claude Code IDE, gptel, clipboard).

* Scope

**In scope**
- Generate and insert/copy a SpecFlow "conversation header" for the active unit/phase
- Include canonical NEXT task text from root =todo.org=
- Include authoritative file pointers from the control plane (unit spec/todo/rules)
- Include parent-chain context pointers (authoritative constraints)
- Provide optional "phase violation" warnings on AI output (heuristic; no enforcement)
- Provide small navigation helpers (jump to control plane, root todo, unit spec)

**Out of scope**
- Managing windows/buffers/layouts
- Sending messages automatically to Claude or GPT
- Applying patches, writing implementation files, committing git changes
- Modifying the control plane automatically
- Deciding what is NEXT (root =todo.org= remains canonical)
- Building context bundles (owned by bundle unit)
- Parsing/writing Org structures (owned by org-store unit)

* MVP Decisions

These decisions shape the MVP implementation:

1. *Header excludes bundle output* — Header provides behavioral contract;
   bundle provides actual context. Two-step workflow for MVP.

2. *No hydrate→bundle dependency* — Hydrate extracts NEXT task independently;
   no transitive dependency on bundle for MVP.

3. *Header = behavioral contract* — The header defines what the AI should do
   in the current phase, not the full codebase context.

4. *Phase definitions in hydrate* — Text templates live in hydrate unit,
   not in core as Elisp constants. Keep it simple.

5. *Insert safety* — Insert prompts for confirmation unless the buffer
   is obviously appropriate (scratch, gptel, claude, chat).

6. *No gptel integration* — For MVP, hydrate is generic. User copies/pastes
   or inserts manually. gptel hooks are a future enhancement.

7. *Guard mode: explicit scans only* — No continuous hooks or automatic
   monitoring. User invokes =scan-buffer= or =scan-region= when desired.

* Header Format

The generated header has this structure:

#+begin_example
Active unit: <unit-name>
Phase: <phase>
Parent chain: <parent → grandparent> or "none"

Files to consult:
- <control-plane-path> (control plane)
- <root-todo-path> (root todo)
- <unit-spec-path> (unit SPEC)
- <unit-todo-path> (unit TODO)
- <unit-rules-path> (unit RULES)
- <parent-spec-path> (parent: <parent-name>)

Allowed actions in this phase:
- <phase-specific action 1>
- <phase-specific action 2>
- ...

STOP conditions:
- If an action would violate the current phase, STOP and ask for confirmation.
- If an interface change is required, STOP and ask for approval.

Canonical NEXT task:
<heading and body from root todo.org>
#+end_example

* Phase Actions

Each phase has specific allowed actions:

| Phase | Allowed Actions |
|-----------+---------------------------------------------------------|
| Plan | Summarize understanding, identify constraints, |
| | propose options. DO NOT write code or specs. |
| Specify | Edit spec.org only. Define outcomes. DO NOT write code. |
| Scaffold | Write CLAUDE.md and todo.org only. DO NOT write code. |
| Implement | Write code and tests strictly per spec. Keep diffs minimal. |
| Validate | Run tests, verify behavior. DO NOT change behavior. |
| Document | Write documentation only. DO NOT change code. |

Unknown phases receive a generic prompt: "Follow phase-specific rules."

* Violation Scanning

Scanning is heuristic-based and non-blocking. Patterns differ by phase:

| Phase(s) | Violation Patterns |
|-------------------------+-------------------------------------------|
| Plan, Specify, Scaffold | Code blocks (```) |
| | Diff headers (+++ / ---) |
| | Diff hunks (@@...@@) |
| | Implementation phrases ("I implemented") |
| | Code keywords (def, function, class, etc) |
| Validate | Behavioral change language |
| Document | Code change language |
| Implement | No warnings (code is expected) |

Scan results are displayed in minibuffer or =*SpecFlow Warnings*= buffer.

* Safe Buffer Detection

Insert commands skip confirmation prompts for "safe" buffers:

- =*scratch*=
- Buffers with "gptel", "claude", or "chat" in the name (case-insensitive)

All other buffers prompt for confirmation before insertion.

* Dependencies

- *org-store*: Control plane discovery and reading
- *bundle*: None (MVP uses independent NEXT extraction)

hydrate does NOT depend on core or bundle.

* Error Handling

| Condition | Behavior |
|-----------------------------+----------------------------------------|
| No control plane found | Signal =specflow-control-plane-not-found= |
| Malformed control plane | Signal =specflow-control-plane-malformed= |
| Unit not found | Signal =specflow-unit-not-found= |
| No NEXT task found | Return placeholder text |
| No todo.org found | Return placeholder text |

* Non-Functional Requirements

- *Deterministic output*: Same inputs produce same header (modulo timestamps)
- *No side effects*: Reading/scanning operations do not modify files
- *Safe defaults*: Copy/preview are always safe; insert prompts when unsure

* Future Enhancements (Post-MVP)

- gptel integration (hooks, automatic header insertion)
- Transient menu for command discovery
- Continuous guard mode (hook-based monitoring)
- Header customization options
- Bundle integration (include context paths in header)
