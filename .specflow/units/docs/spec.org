#+TITLE: docs – Specification
#+STARTUP: overview

* Purpose

The docs unit produces user-facing documentation for SpecFlow.

Target audience: Developers who want to use SpecFlow for their own projects.

* Scope

**In scope**
- Root README.md (project entry point)
- Links to existing unit READMEs

**Out of scope**
- Unit-level READMEs (already exist, owned by respective units)
- Internal design docs (overview.org, architecture.org owned by core)
- API documentation or docstrings

* Artifacts

** Root README.md

Location: Repository root (`README.md`)

Length: 200-300 lines

*** Required Sections

1. *Title and Tagline*
   - "SpecFlow"
   - One-line description: Org-native, spec-driven, phase-gated AI-assisted development

2. *What is SpecFlow*
   - 2-3 paragraphs explaining the problem and solution
   - Not a full methodology guide, just enough to understand the value

3. *Installation*
   - Prerequisites (Emacs 27.1+)
   - Clone repo
   - Add to load-path
   - Require specflow

4. *Quick Start*
   - 5-step workflow to get started:
     1. Create control plane (docs/specflow.org)
     2. Set phase and active unit
     3. Run specflow-hydrate-copy-header
     4. Paste into AI chat
     5. Work within phase constraints
   - Include minimal code examples

5. *Commands Overview*
   - Table of all public commands grouped by module
   - Brief description of each
   - Link to unit README for details

6. *Module Documentation*
   - Links to:
     - units/org-store/README.md
     - units/bundle/README.md
     - units/hydrate/README.md

7. *The SpecFlow Workflow*
   - Brief explanation of phases: Plan → Specify → Scaffold → Implement → Validate → Document
   - One sentence per phase describing what's allowed
   - Not a full methodology guide

8. *Project Structure*
   - Explain expected repo layout:
     - docs/specflow.org (control plane)
     - todo.org (root tasks)
     - units/<name>/ (unit directories)

9. *License*
   - State the license (if applicable)

*** Style Guidelines

- Write for someone new to SpecFlow but familiar with Emacs
- Use code blocks for all Elisp examples
- Prefer tables over prose for command listings
- Keep explanations brief; link to unit READMEs for depth
- No emojis

* Constraints

1. Do not duplicate content from unit READMEs; link instead
2. Do not explain internal architecture; that's in architecture.org
3. Do not write a full SpecFlow methodology guide; keep practical
4. Maximum 300 lines for root README

* Success Criteria

Given a developer unfamiliar with SpecFlow,
when they read the root README,
then they can:
- Understand what SpecFlow does (under 2 minutes)
- Install it (under 5 minutes)
- Run their first hydrate command (under 10 minutes)
- Know where to find detailed docs for each module
