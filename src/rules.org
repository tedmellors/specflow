#+TITLE: SpecFlow – Operational Rules
#+STARTUP: overview

* Scope
  :PROPERTIES:
  :RULE_ID: scope
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: philosophy overview
  :END:

This repository follows the **SpecFlow philosophy**:
a **spec-driven, phase-gated workflow** for AI-assisted software development.

The system is organized into **units** (modules, services, components), each with:
- an explicit specification
- outcome-based TODOs
- unit-level constraints
- a well-defined lifecycle phase

This repository is intended for **real use**, not demos or throwaway prototypes.

"Production-ready" means:
- reliable within the stated scope
- testable and verifiable
- auditable where reasoning or decisions occur
—not feature-complete or infrastructure-final.

* Control Plane Authority
  :PROPERTIES:
  :RULE_ID: control-plane-authority
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: control-plane startup
  :END:

The current operational state of this repo is defined by the SpecFlow control plane:
- =.specflow/specflow.org=

Before starting any work, you MUST:
1) Read the control plane
2) Identify the active unit and phase
3) Follow the phase rules for that phase

If there is a conflict between task focus in chat and the control plane,
the control plane is authoritative for: active unit, phase, and unit pointers.

* Task Discovery
  :PROPERTIES:
  :RULE_ID: task-discovery
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: todo tasks
  :END:

Canonical NEXT task source is =.specflow/todo.org=.

When asked "what is the NEXT actionable task":
1) Open =.specflow/todo.org=.
2) Find the first heading marked =NEXT=.
3) Return that exact heading and its immediate bullets/subtasks as the actionable plan.
4) Do NOT use unit-level todo files to choose NEXT unless =.specflow/todo.org= explicitly points there.
5) If no =NEXT= exists, propose 1–3 candidate NEXT tasks and ask for confirmation.

If the NEXT task explicitly references a unit, treat that unit as the execution target,
but do NOT change the active unit in the control plane unless explicitly instructed.

* Parent Context
  :PROPERTIES:
  :RULE_ID: parent-context
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: hierarchy units
  :END:

Units may declare hierarchy in the control plane (e.g., =PARENT= / =CHILDREN= properties).

When working on a unit:
1) Read =.specflow/specflow.org= to identify the active unit and its =PARENT= chain (if any).
2) Before implementing or changing behavior in the unit, review parent unit specs/docs referenced by the control plane.
3) Treat parent unit constraints and invariants as authoritative.
4) If a child unit spec conflicts with a parent constraint, STOP and ask for resolution (do not implement).

* Context References
  :PROPERTIES:
  :RULE_ID: context-refs
  :PRIORITY: recommended
  :PHASE: all
  :TAGS: context units
  :END:

Units may declare additional context via a =CONTEXT_REFS= property in the control plane.

Semantics:
- =PARENT= chain docs/specs are **authoritative constraints**.
- =CONTEXT_REFS= are **advisory context** to read for additional background, examples, or rationale.
- If =CONTEXT_REFS= conflicts with parent constraints or the unit spec, parent/spec win.

When working on a unit:
1) Read the control plane entry for the active unit.
2) If =CONTEXT_REFS= is present, read those references before implementing changes.
3) Treat them as context only (not requirements) unless the unit spec explicitly promotes them to requirements.

* Bootstrapping the Master TODO
  :PROPERTIES:
  :RULE_ID: bootstrap-todo
  :PRIORITY: recommended
  :PHASE: scaffold
  :TAGS: todo bootstrap
  :END:

If the repo does not yet have =.specflow/todo.org=, do **NOT** create one automatically.

Only generate an initial =.specflow/todo.org= when I explicitly request it
(e.g., "bootstrap the master todo" / "create todo.org").

When prompted to bootstrap:
- Treat this as a Scaffold task.
- Do NOT write implementation code.
- Read the highest-level context (overview/architecture and any parent chain docs).
- Produce =.specflow/todo.org= that:
  - defines phases (Plan → Specify → Scaffold → Implement → Validate → Document)
  - lists major units/modules in dependency order
  - contains exactly ONE =NEXT= task that is actionable and outcome-based
- STOP and request approval before making any other project changes.

* Documentation Pipeline
  :PROPERTIES:
  :RULE_ID: documentation-pipeline
  :PRIORITY: recommended
  :PHASE: all
  :TAGS: docs artifacts
  :END:

This repo uses a top-down documentation pipeline:

1) Parent unit spec (=.specflow/units/docs/spec.org=) - project intent and architecture
2) =.specflow/todo.org= - execution plan
3) Unit specs/todos in =.specflow/units/<unit>/= - scoped implementation

These artifacts are created or updated **only when explicitly requested**.
Do not generate or modify them "opportunistically."

** Parent Unit Spec

The parent unit (typically =docs=) owns the project-level specification.
This spec defines project intent, architecture, and cross-cutting constraints.

When I ask to draft or revise the parent unit spec:
- stay high-level (no module internals)
- prefer clear constraints and examples
- capture open questions explicitly
- STOP and request review before proceeding

** .specflow/todo.org (Execution Layer)

The =.specflow/todo.org= file is the canonical task driver.
It is generated from the parent unit spec **only when prompted**.

When I ask to bootstrap or revise =.specflow/todo.org=:
- produce a phase-structured roadmap
- include exactly ONE =NEXT= task
- keep tasks outcome-based (Given/When/Then style)
- preserve DONE history if updating an existing file
- STOP and request approval before proceeding to unit work

** Unit-level work (Child Units)

Child units are created/refined only after =.specflow/todo.org= explicitly points to them.

When =.specflow/todo.org= points to a unit:
- consult parent chain specs (if declared) before implementation
- create/update unit =spec.org= and =todo.org= in =.specflow/units/<unit>/= per phase rules
- do not skip phases or jump to implementation

* Master TODO to Unit Handoff
  :PROPERTIES:
  :RULE_ID: todo-unit-handoff
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: todo units handoff
  :END:

When the =.specflow/todo.org= NEXT task points to a specific unit:

1) Treat that unit as the execution target (do not change control plane unless instructed).
2) Read parent chain specs/docs first (PARENT), then the unit spec/todo.
3) Perform work only for the current phase:
   - Plan: design/options/questions only
   - Specify: edit unit =spec.org= only
   - Scaffold: edit unit =todo.org= only
   - Implement: code + tests only
   - Validate/Document: no behavior changes
4) STOP and request approval at the end of each phase deliverable.

* Global Rules
  :PROPERTIES:
  :RULE_ID: global-rules
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: rules constraints
  :END:

1. **One unit at a time.**
   Only edit files within the active unit unless explicitly authorized.

2. **Interface discipline.**
   Cross-unit interfaces or contracts must live in a designated location
   (e.g. =docs/interfaces/=, =interfaces/=, or equivalent).

   To change an interface:
   - Update the interface definition
   - Write an ADR explaining the change
   - **STOP. Do not implement. Wait for explicit approval.**

   If approval is not granted, explain why the change is required and halt.

3. **Spec-driven development.**
   Each unit has a spec (1–2 pages max).
   Implement **only** what is explicitly stated.
   Do not infer or extend requirements.

   If behavior is unclear or missing, update the spec or ask before proceeding.

4. **Smallest possible change.**
   Prefer the minimal diff needed to satisfy the spec or active TODO.
   Do not refactor, rename, or reorganize code unless required.
   No temporary, backward-incompatible, or partial interface changes.

5. **Testing is mandatory.**
   Every behavior change must include corresponding test updates.
   Tests should cover only the changed or newly specified behavior.
   Do not rewrite unrelated tests or introduce new frameworks.

6. **Auditability where applicable.**
   For analytical, ranking, comparison, or recommendation outputs:
   - Claims must cite evidence
   - Comparisons must explain rationale
   - Outputs must be traceable to inputs

   Do not add unnecessary explanation for purely mechanical code.

7. **Avoid scope creep.**
   Do not introduce new units, workflows, abstractions, or architectural patterns
   unless explicitly requested.

8. **TODOs describe outcomes, not tasks.**
   When writing TODOs, avoid:
   - "Implement X"
   - "Refactor Y"

   Prefer:
   - "Given A, when B, then C"
   - "Function returns structure {…}"
   - "Latency p95 < 200ms on dataset D"
   - "Unit tests cover parser edge cases: …"

9. **Phase violations require confirmation.**
   If an action would violate the current phase, **STOP and ask for confirmation**.

* Source of Truth
  :PROPERTIES:
  :RULE_ID: source-of-truth
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: control-plane org
  :END:

This repository uses an **Org-mode control plane**
(=.specflow/specflow.org=) to store:
- the active unit
- the current phase
- canonical pointers to specs and TODOs

Org files (=.org=) are the authoritative source for:
- specifications
- planning documents
- ADRs
- TODOs

Markdown (=.md=) files are created **only** when explicitly requested
(e.g. README files for external users).

* Unit Structure
  :PROPERTIES:
  :RULE_ID: unit-structure
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: units structure
  :END:

SpecFlow uses a hidden =.specflow/= directory at the project root for all development artifacts.

** Fixed Structure (Required)

The =.specflow/= directory and =CLAUDE.md= are required and have a fixed structure:

#+BEGIN_EXAMPLE
project/
├── .specflow/
│   ├── specflow.org          # Control plane (active unit, phase)
│   ├── todo.org              # Root task list
│   ├── rules.org             # Operational rules (generates CLAUDE.md)
│   └── units/
│       ├── docs/
│       │   ├── spec.org      # Parent unit specification
│       │   └── todo.org      # Parent unit tasks
│       └── <unit>/
│           ├── spec.org      # Unit specification
│           └── todo.org      # Unit tasks
├── CLAUDE.md                 # Generated from .specflow/rules.org
└── ...                       # Project source (see suggested layouts below)
#+END_EXAMPLE

Unit scope and constraints are defined in =spec.org= (no separate CLAUDE.md per unit).

** Suggested Layouts

Project source structure is flexible. Choose a layout that fits your project:

*** Template A: Simple

For libraries, CLI tools, single services, Emacs packages.

#+BEGIN_EXAMPLE
project/
├── .specflow/
├── src/                      # All source code
├── tests/                    # All tests
├── CLAUDE.md
└── README.md
#+END_EXAMPLE

*** Template B: Frontend + Backend

For web apps and full-stack projects (often polyglot).

#+BEGIN_EXAMPLE
project/
├── .specflow/
├── frontend/
│   ├── src/
│   ├── tests/
│   └── package.json
├── backend/
│   ├── src/
│   ├── tests/
│   └── pyproject.toml        # or go.mod, Cargo.toml, etc.
├── CLAUDE.md
└── README.md
#+END_EXAMPLE

*** Template C: Monorepo

For large projects, microservices, or multiple related apps.

#+BEGIN_EXAMPLE
project/
├── .specflow/
├── apps/
│   ├── web/
│   └── api/
├── packages/                 # or libs/
│   └── shared/
├── CLAUDE.md
└── README.md
#+END_EXAMPLE

Adapt these templates to your project's needs. The =.specflow/= structure is fixed; source layout is guidance.

* Specification Structure
  :PROPERTIES:
  :RULE_ID: spec-structure
  :PRIORITY: recommended
  :PHASE: specify
  :TAGS: spec template structure
  :END:

** Required Sections

- **Purpose** — Why this unit exists, what problem it solves. 1–3 paragraphs, no implementation detail.
- **Scope** — Must have In Scope/Owns (bullet list) and Out of Scope/Does Not Own. Anything not listed under In Scope is forbidden.
- **Public Interface** — Inputs, outputs, commands or API functions. Changes trigger the interface-change protocol.
- **Testing Requirements** — Minimum required test coverage with Given/When/Then format. Implementation refused without tests for each item.

** Recommended Sections (when relevant)

- **Invariants** — Testable truths: determinism, idempotency, ordering guarantees.
- **Error Handling** — Hard failures (signal error, abort) vs soft failures (warn, fallback).
- **Dependencies** — Upstream (what this unit depends on) and downstream (who depends on it).
- **Non-Goals** — What this unit will NOT do.
- **Open Questions** — Must be empty or acknowledged before implementation.
- **Plan Notes** — Dated decisions and rationale.

** Section Order

Purpose → Scope → Public Interface → Invariants → Error Handling → Dependencies → Testing Requirements → Non-Goals → Open Questions → Plan Notes

** Quality Checks

When reviewing or writing a spec:
- Scope boundaries are explicit (not vague)
- Public interface is specific enough to implement against
- Testing requirements use Given/When/Then format
- No implementation details leak into the spec
- Open questions are acknowledged (not silently deferred)

* Operating Procedure
  :PROPERTIES:
  :RULE_ID: operating-procedure
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: workflow procedure
  :END:

Before starting any task:
1. Identify the active unit
2. Identify the current phase from the control plane
3. State the phase explicitly
4. Follow the phase enforcement rules below

When working on a task:

1. Read:
   - project overview / architecture docs (if relevant)
   - unit =spec.org= (in =.specflow/units/<unit>/=)
   - unit =todo.org= (active =NEXT=)
   - unit =README.md= (if it exists)

2. Work **only** within the active unit unless explicitly authorized.

3. If an interface change is required:
   - Propose the change
   - Update the interface definition
   - Draft an ADR
   - **STOP and wait for approval**

4. When finished:
   - Update tests
   - Update specs/docs if behavior changed
   - Commit changes (or provide exact git commands)
   - Mark the =NEXT= task as DONE
   - Summarize:
     - what changed and why
     - files touched
     - tests run and results
   - Propose the next =NEXT= task

* Phase Transition Protocol
  :PROPERTIES:
  :RULE_ID: phase-transition
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: phase transition
  :END:

When completing a phase within a unit:

1. **Update .specflow/todo.org**:
   - Mark current NEXT task as DONE with 1-2 line summary
   - Create new NEXT task for the next phase (if not unit complete)

2. **Update control plane** (.specflow/specflow.org):
   - Change SPEC_FLOW_PHASE property to the next phase

3. **Entry format in .specflow/todo.org**:

   #+BEGIN_EXAMPLE
   ** DONE <unit>: <phase> phase
      CLOSED: [YYYY-MM-DD]
      <1-2 line summary: what was accomplished, key decisions>

   ** NEXT <unit>: <next-phase> phase
      <brief: what this phase will produce>
   #+END_EXAMPLE

4. **Phase progression**:
   - Plan → Specify
   - Specify → Scaffold
   - Scaffold → Implement
   - Implement → Validate
   - Validate → Document
   - Document → unit complete (mark DONE, no new NEXT unless backlog)

This creates an audit trail and allows resumption at exact phase.

* Phase Enforcement
  :PROPERTIES:
  :RULE_ID: phase-enforcement
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: phase rules
  :END:

Each unit progresses strictly through:

**Plan → Specify → Scaffold → Implement → Validate → Document**

| Phase     | May Edit                | Must NOT Edit            |
|-----------+-------------------------+--------------------------|
| Plan      | nothing (read-only)     | all files                |
| Specify   | spec.org                | code, todo.org           |
| Scaffold  | unit todo.org           | code, spec.org           |
| Implement | all files               | nothing                  |
| Validate  | test files              | source, specs            |
| Document  | docs, specs, todos      | source code              |

The =.claude/hooks/phase-guard.sh= hook enforces these rules at runtime.
Phase-specific agents carry detailed guidance for their phase.

* Patch Protocol
  :PROPERTIES:
  :RULE_ID: patch-protocol
  :PRIORITY: recommended
  :PHASE: all
  :TAGS: patch workflow quick-fix
  :END:

For trivial changes, the full phase workflow is unnecessary.
Use the Patch protocol as a single-step fast path.

** Qualifies for Patch

ALL of the following must be true:

- Single-file change (or 2-3 files for tightly coupled edits like test + source)
- No behavior change OR obvious bug fix with clear root cause
- No interface change (public API, function signatures, data structures)
- No new tests required (or only trivial test updates)
- No design decisions involved
- Change is self-evidently correct

Examples:
- Typo fixes in docs or comments
- Fixing an obvious off-by-one error
- Updating a constant or config value
- Adding a missing import
- Renaming a local variable
- Fixing broken formatting

** Does NOT Qualify

If ANY of these apply, use the full phase workflow:

- Behavior change that isn't an obvious bug fix
- Any interface or contract change
- Multi-file refactoring
- New feature (even small ones)
- Change requires design discussion
- Uncertainty about correctness
- Change touches code you don't fully understand

When in doubt, use the full workflow.

** Patch Process

1. **State intent**: "Patch: <one-line description>"
2. **Show the change**: Display the exact diff or edit
3. **Apply**: Make the change
4. **Verify**: Run relevant tests or validation
5. **Commit**: Single commit with message: "patch: <description>"

No phase transitions, no control plane updates, no TODO entries.

** Audit Trail

Patches are tracked via git commits only.
The "patch:" prefix in commit messages identifies fast-path changes.

If a patch grows in scope during execution, STOP and convert to full workflow.

* Bug Protocol
  :PROPERTIES:
  :RULE_ID: bug-protocol
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: bugs issues
  :END:

When a bug or runtime issue is discovered:

1. **Investigate only**
   - Identify root cause
   - Do NOT modify code

2. **Document the issue**
   - Add a high-level entry to the project TODOs
   - Add a detailed entry to the unit =todo.org=, including:
     - symptoms
     - root cause
     - proposed fix (with rationale)

3. **STOP and present findings**
   - What went wrong
   - Why it happened
   - Proposed fix (and alternatives)
   - Files that would change

4. **Wait for explicit approval** before implementing

This applies even to "simple" or obvious fixes.

* TODO File Format
  :PROPERTIES:
  :RULE_ID: todo-format
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: todo format structure
  :END:

=.specflow/todo.org= uses three sections: Active, Backlog, Completed.
- Exactly ONE =NEXT= task in Active (the current focus)
- Tasks are outcome-based (Given/When/Then), not action-based
- =DONE= tasks move to Completed with =CLOSED: [YYYY-MM-DD]= and brief summary
- Do NOT leave DONE tasks in Active

** File Template

#+BEGIN_EXAMPLE
  #+TITLE: <unit> – Tasks
  #+STARTUP: overview
  #+SEQ_TODO: TODO NEXT WAITING | DONE

  * Active

  ** NEXT <first task>
     Given ..., When ..., Then ...

     Acceptance criteria:
     - ...

  ** TODO <second task>
     ...

  * Backlog

  * Completed
#+END_EXAMPLE

** Section Rules

- **Active**: Exactly ONE =NEXT= task. Remaining ranked by dependency as =TODO=. Each task has Given/When/Then and acceptance criteria.
- **Backlog**: Less immediate or lower priority. May need refinement before activation.
- **Completed**: =DONE= tasks with =CLOSED: [YYYY-MM-DD]= and 1-2 line summary.

** Completing a Task

1. Change =NEXT= or =TODO= to =DONE=
2. Add =CLOSED: [YYYY-MM-DD]= timestamp
3. Add brief summary (1-2 lines)
4. Move the entry from Active to Completed section

** Scaffold Process

When creating a unit todo.org from its spec:
1. Read spec.org and parent spec (if PARENT declared)
2. Identify all behaviors, interfaces, and testing requirements
3. Break into implementable tasks with clear acceptance criteria
4. Order by dependency (foundations first)
5. Mark the first task as NEXT

* Checkpoint Commits
  :PROPERTIES:
  :RULE_ID: checkpoint-commits
  :PRIORITY: mandatory
  :PHASE: scaffold document
  :TAGS: git commits workflow
  :END:

Certain phases require a commit and push checkpoint before proceeding:

1. **After Scaffold phase**: Commit and push the scaffolded =todo.org=
2. **After Document phase**: Commit and push documentation changes

This ensures:
- Work is preserved before moving to implementation
- Documentation is captured before starting new work
- Progress can be resumed from known checkpoints

Format: =git commit -m "<unit>: <phase> phase complete"= then =git push=

This is a workflow convention for Claude to follow, not system-enforced.

* Phase Transition Stops
  :PROPERTIES:
  :RULE_ID: phase-transition-stops
  :PRIORITY: mandatory
  :PHASE: all
  :TAGS: phase transition workflow
  :END:

This directive governs Claude behavior and cannot be system-enforced.

At EVERY phase transition, Claude MUST:

1. **STOP** and announce the phase is complete
2. **Summarize** what was accomplished in the phase
3. **Wait** for explicit confirmation before proceeding

Do NOT auto-advance through phases. Even if the next phase seems obvious,
wait for the user to say "proceed to <phase>" or equivalent.

Example transition announcement:
#+BEGIN_EXAMPLE
Specify phase complete.

Summary: Added 3 new rules to rules.org (todo-format, checkpoint-commits,
phase-transition-stops).

Ready to proceed to Scaffold phase when you confirm.
#+END_EXAMPLE

This applies to ALL phase transitions:
- Plan → Specify
- Specify → Scaffold
- Scaffold → Implement
- Implement → Validate
- Validate → Document
